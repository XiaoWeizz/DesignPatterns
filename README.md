# 结构型

## 1.Adapter-适配器

作用：

- 将不完美的类和方法，完美适配应用需要的类和方法。

应用理由：

如果现有的代码可以完美满足应用的调用，那确实不需要使用适配器模式。但应该很少有这种情况。现实往往是应用在实现业务需求时需要各种各样功能的类和方法，还可能随业务需求变化而变化。当被调用的代码是我们自己本身负责时，大概率也不需要使用适配器模式，白白增加工作量，不如直接修改被调用的代码，或者增加完美适配的方法就行了。除非，一是被调用代码不是自己写的代码，或干脆只能看到接口，例如第三方提供；二是被调用代码概念非常清楚，修改或增加方法可能会破坏其完美性。适配器模式允许稳定的代码不必为了业务变化而变化。

## 2.Bridge

作用：

- 将一个类按其不同的变化维度拆分并组装起来，使其不同维度可以独立扩展。

应用理由：

能想到的应用场景并不多，通信框架库是目前本人遇到的最契合这个模式的场景。研究其原理，其实就是把类中的几个方法单独拎出来做成接口，使用接口隔离其实现的变化，就像公司把产品的某些子产品外包出去一样。日常开发，基本用不到，不用就不用吧，反正也很简单。

## 3.Composite

作用：

- 将一个有嵌套结构的对象拆解成多个相似的对象，方便应用统一调用。
- 将对象组合成树形结构以表示 “部分-整体” 的层次结构，使得用户对单个对象和组合对象的使用具有一致性。

应用理由：

要使用这个模式必须满足两个要求，一是对象可以构建树结构；二是每个节点有共同方法。满足这两个条件之后，使用这个模式的好处也是显而易见的了。应用要操作一个嵌套对象时，和处理单个对象是没有区别的，应用逻辑就能变得简单。比如常见的树结构菜单，节点的数据和操作方法都可以封装在节点对象中，同样的显示方法，就能容易做个性化的显示。xml文件，UI控件等都很适合使用组合模式。

## 4.Decoractor

作用：

- 在原始方法上增加行为，使得原方法和新方法同时存在。
- 多个新增的行为可以动态叠加。

应用理由：

装饰，顾名思义，在原有的基础上增加额外的东西，原来的东西没变。也就是说，原来的方法是不变的，可能只是增加了新的字段，于是类增加了额外的行为，但是新行为不会影响原本的行为。这种情况下，装饰器避免了原始类的膨胀。另外的好处是可以动态叠加，比如普通员工加上审批流程的行为变成了领导，去掉额外的职责就是普通的员工，这样员工就可以在软件运行时增加不同的行为变成不同的角色。

## 5.Facade

作用：

- 将一个复杂的功能分解到子类去实现，对外保持简单。
- 封装多个类的协作来完成应用的功能。

应用理由：

一个庞大的类，应该将其分解为小的类，简化应用调用的同时，保持内部实现的代码整洁。换个角度，当已有的很多类需要需要一些协作才能完成一个功能时，考虑把他封装在Facade类中，并给他起一个贴切的名称。资深程序员一定懂，这样做很酷。

## 6.Flyweight

作用：

- 通过共享对象来减少应用中的内存分配。

应用理由：

如果用纯面向对象方法去设计一个像编辑器的系统，那每个字母都是一个对象，而一篇文章有很多字母，那重复的字母就会浪费很多内存，而使用享元模式最多创建26个字母的对象。那有人就会质疑了，编辑器可不会只有字母，还有汉字，而一篇文章可没多少重复的汉字哦。对，质疑的好，但我为什么一定要举这个编辑器例子呢？因为没有比这个更简单容易懂，又很贴合享元模式的例子了。对于一个普通程序员来说，很难遇到使用享元的例子的。就说这个编辑器，库肯定有一个方法，输入文本内容就直接绘制出来了，哪需要这么麻烦每个字母构建一个对象呢。那这个模式有什么用呢？有，有高级用法，但是需要配合其他模式使用，例如依赖注入和控制反转，我去深造一下，咱们高级篇见。

## 7.Proxy

作用：

- 把一个对象交给代理对象，由代理对象控制原对象的行为。

应用理由：

代理模式和对象适配器的结构是一模一样的，但是有两个点要注意，一是适配器允许原对象接口不一致，而代理模式不允许；二是适配器可能改变原对象的行为，而代理只是控制原对象什么时候行为(不改变行为的内容)。如果增加一些权限检查，日志记录这些给行为锦上添花的逻辑，代理模式正合适。当然，本人觉得没必要区分用代理还是适配器，那是留给死板的人去想的，你只要会使用这种隔离机制就行。千万不要直接使用Adapter,Proxy这样的字眼去命名你的类，这样做会浪费时间去纠结到底用哪个是准确，况且到最后就算命名对了，也对代码理解毫无用处，不如直接用类的用意去命名。
